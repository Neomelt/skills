# 根因溯源与边界取证模式

当缺陷深埋在调用栈底部或横跨多个组件时，按需采用以下三种定位手法，避免在表象处打补丁。

## 1. 向后溯源（Backward Tracing）

报错点往往只是“受害者”，真正的肇事者在调用链上游：

1. **锁定直接触发点**：记下报错行直接消费了哪个非法值（如空路径、越界索引、过时状态）。
2. **逐层反问调用方**：谁把这个值传进来的？传进来之前它是什么？
3. **追到源头再下刀**：一路回溯到该值首次被构造或被破坏的位置，在源头修复；随后在下游关键边界加轻量断言（Defense-in-Depth），防止未来同类脏数据再次静默穿透。

## 2. 多组件边界插桩

面对跨进程、跨语言或前后端联动故障（如 CLI → Daemon → API，或配置 → 构建 → 运行时），不要直接猜哪一层坏了：

1. 列出数据经过的所有交界点（A → B → C）。
2. 在每个交界点的入口与出口各打一条一次性诊断日志（记录关键变量、环境变量、工作目录与返回值）。
3. 跑一次复现，用二分法直接锁定“A 出正确、B 入错误”的断裂边界，只深挖那一层。
4. 修复完成后务必清理所有临时诊断日志。

## 3. 用条件等待替代拍脑袋 `sleep`

遇到异步、UI 动画、进程启动或硬件通信的偶发竞态失败时：

- **禁止**通过不断加大固定延时（`sleep(500)` → `sleep(2000)`）掩盖竞态。
- 查清真正缺失的同步信号（事件回调、文件/端口就绪、状态机切换完成），改用带超时上限的**显式条件轮询或事件监听**，让等待与真实状态绑定。
