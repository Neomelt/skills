# Root Cause Debug（根因排障与验证闭环）

针对“盲目猜原因 → 叠补丁 → 越修越脏”的工程刹车片。核心只有两条铁律：

1. **未完成根因取证前，严禁修改业务代码或提出修复补丁**。
2. **未拿到当轮新鲜的验证输出前，严禁宣称“已修复”或“测试通过”**。

## 四阶段排障流程

按顺序推进，不跳步：

### 1. 根因取证（只观察，不动业务代码）

- **通读完整错误与栈帧**：不要只扫第一行报错，核对行号、错误码与前后警告。
- **建立稳定复现**：明确触发命令或输入步骤；无法稳定复现时先补日志收集证据，绝不靠猜。
- **核查近期变更**：先看 `git status`、`git diff` 与最近提交，排除新依赖、配置漂移或环境差异。
- **多组件边界插桩 / 向后溯源**：跨越多个模块或进程时（如前端 → API → 服务 → 数据库，或脚本 → 仿真 → 硬件），先在组件交界处打印入参、出参与关键状态，定位**具体在哪一层首次出现异常**，再沿调用栈向后追查坏值的原始来源（具体手法见 [references/tracing-patterns.md](references/tracing-patterns.md)）。

### 2. 对照正常路径

- 在同一仓库内找到能正常工作的同类实现，逐项比对配置、前置条件、数据结构与生命周期顺序的差异，不放过看似微小的细节。

### 3. 单一假设与最小证伪

- 明确写出单一可证伪假设：**“我认为根因是 X，因为证据 Y”**。
- 一次只变动一个变量做最小验证；若假设被推翻，先撤回试探改动再提出新假设，**严禁在无效补丁上继续叠加补丁**。

### 4. 根治修复与验证闭环

- **先落复现用例**：优先写一个能稳定复现原缺陷的自动化测试（或最小复现脚本），确认其在修复前必然失败。
- **单一源头修复**：只针对已证实的根因下刀，不顺手混入无关重构；必要时在关键入口补上防御性校验（Defense-in-Depth）。
- **新鲜证据验收**：在当前回复中实际运行验证命令（复现测试 + 受影响模块测试/构建），完整读取退出码与输出确认 0 失败，再如实汇报“根因是什么、改了哪里、验证输出如何”。

## 三次失败熔断机制

- 记录对同一问题的有效修复尝试次数：
  - **< 3 次失败**：带着新观察到的现象退回阶段 1 重新分析。
  - **≥ 3 次失败**（或每次修复都在别处引发新症状、需要大面积拆东墙补西墙）：**立刻停手，禁止尝试第 4 次修复**。这通常意味着底层状态设计或模块耦合本身存在架构问题，先向用户呈现已排除的路径与架构症结，讨论后再定夺。

## 踩坑与红旗自检（Red Flags）

脑中闪过以下念头时，说明正在滑向“治标补丁”，立即刹车回到阶段 1：

- “先加个 `setTimeout` / 容差 / `try-catch` 吞掉报错看看行不行”
- “问题很简单，直接改一下应该就好了”
- “顺便把旁边两处可疑代码也一起改了再测”
- “之前跑过测试，这次小改应该不会坏，不用重跑了”
- 向用户汇报时出现“应该已经修好了”“大概率没问题”等无实测支撑的措辞
