# Pragmatic Engineering（务实软件工程与反过度设计准则）

提炼自 20 年工业级开源实战（参考 Martijn Faassen 工程笔记）的核心判断力：**软件工程没有脱离语境的绝对教条，高手的核心能力是在当下规模与长期演化之间做出恰如其分的权衡（Right-engineering）**。

## 一、恰如其分，警惕两个极端

- **先跑通，再演化（Make it work first）**：不要试图关起门来一次性设计出“终极架构”。先做出能跑通核心路径的简单版本，借自动化测试与真实使用反馈驱动重构。
- **严禁过度工程（Over-engineering）**：
  - 禁止为“未来也许会用到”的假想需求提前堆砌插件系统、多层工厂、多余接口或过早拆微服务。没有真实业务锤炼过的预设扩展点，未来真要用时也往往是对不上的。
  - **把“最佳实践”当警铃，不当大棒**：DRY、全员 PR、分层解耦都是默认护栏而非死律。决定采用或打破某条惯例时，必须说清**在当前项目规模、团队人数与维护周期下的真实收益与代价**。

## 二、抽象与重复的边界（Repeat Yourself, A Bit）

- **允许适度重复，等变化轴线浮现再抽象**：
  - 过早高层抽象最大的隐患是扼杀 **“90% 相同 + 10% 例外”** 的定制需求。业务代码先允许重复两三次，把重复当作观察真实共性的设计压力，看清边界再一次性抽准。
  - **测试代码与声明式配置优先自包含**：单个测试用例把前置数据和断言摊在眼前、能独立看懂和修改，比抽成一堆多层嵌套的隐式 fixture 更值钱。
- **顺手“种出”自己的微型内部框架**：
  - 当外部大框架为了通用性迫使代码写得极其别扭、或同一类业务样板反复出现时，可抽一个聚焦的声明式小模块（内部库/微框架）。
  - 用开源项目的标准对待它（配齐测试与文档），趁早期用户少时大胆塑形 API；一旦定型，**全仓统一迁移到新模式**，避免新旧两套示范代码并存污染后续开发。

## 三、清晰度、类型表达与理性优化

- **朴素可读优先于炫技写法**：
  - 简单线性转换用声明式链（如 `.map().collect()`）既清晰又高效；一旦涉及复杂状态累积、`break` / `return` 早退或 `?` 错误传播，果断使用朴素的 `for` 循环，不为了“函数式洁癖”折磨读代码的人。
- **用和类型（Sum Types）压缩非法状态**：
  - 在支持代数数据类型的语言（如 Rust `enum`、TypeScript 联合类型）中，优先用互斥变体配合穷尽匹配表达领域状态，而非散落的 `bool` 标志位或笨重的 OOP 继承树。
- **理性看待性能优化（不神化也不纵容臃肿）**：
  - **拒绝邪恶的过早优化**：不牺牲可读性去抠无意义的底层微优化，不为幻想的高并发引入重型基础设施。
  - **坚持顺手的正确优化**：用哈希表查找替代线性扫描、在明显高频路径上加现成索引，这类改动**既更快又更简洁，永远不算“过早”**；警惕层层堆叠无用依赖导致的复杂度膨胀。

## 四、AI 协作下的心智模型守护（Sigh Coding 纪律）

- **拒绝一口气黑盒生成庞大架构（Big Design Up Front）**：面对复杂模块或新系统，采用小步增量推进，每一步都让改动保持在人类可审视、可解释的粒度内。
- **主动留出“慢下来消化”的检查点**：AI 产出代码很快，但人类建立对代码库的真实理解（Theory Building）天生是慢的。重大模块落地或连续多轮快速迭代后，主动停下来帮用户梳理核心数据流、状态边界与“为什么这样设计”，防止用户在自己的仓库里沦为只知功能、不知原理的“新入职陌生人”。
- **改现有仓库先读契约**：动手前先读懂项目既有风格、分层与约束，能通过删减与理顺解决的问题，绝不靠叠加新抽象层掩盖。
